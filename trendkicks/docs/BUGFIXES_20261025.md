## Firebase configuration still needed for real Android push

The downloaded Android `google-services.json` has now been imported into the ignored local build config, including its four public FCM values. Keep those files locally. The following steps document the configuration for another checkout; in-app notifications require none of this setup.

1. In Firebase Console, create/select a free project and register an Android app with the existing package **`com.example.trendkicks`**. Download its **Android `google-services.json`**, not a service-account file.
2. Put it at `android/app/google-services.json` (ignored by Git) and import only its public values:

```powershell
node tools/configure_firebase.mjs android/app/google-services.json
```

This preserves existing Supabase values in ignored `config/local.json` and adds `FCM_API_KEY`, `FCM_APP_ID`, `FCM_SENDER_ID`, `FCM_PROJECT_ID`. Initialization is programmatic, so no Google Services Gradle plugin or generated `firebase_options.dart` is required for this configuration path. The four public values can also be entered directly from the Android app settings. Do not invent placeholder values for a working build.

3. For **server delivery**, enable Firebase Cloud Messaging HTTP v1 and put the matching Firebase service-account JSON only in the Supabase `FCM_SERVICE_ACCOUNT_JSON` Edge secret. Never place its private key in Flutter, assets or `local.json`.
4. Keep the private `STORE_JOB_SECRET` and the existing cloud `store-jobs` schedule from [advanced setup](ADVANCED_SETUP.md). Registering a phone alone does not run the delivery worker.
5. Rebuild/reinstall the APK with this public config. Use an internet-connected Android phone with Google Play services. On Android 13+, allow notification permission. If denied, use **Android notification settings**, allow Trend Kicks, return and enable push again. If configuration, permission, token retrieval or database registration fails, the switch stays off with a useful error.

Backend events already support verified payment, normal order-status changes, earned rewards, exact-variant restock and support replies. Test each through a real sandbox/demonstration action. The queue rechecks preference and current token ownership before sending; disabling optional push preserves in-app history.
